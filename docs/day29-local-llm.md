# День 29. Оптимизация локальной LLM

Локальная Qwen 3.5 9B настроена для RAG-ответов на русском по главе 6
Java Concurrency in Practice. Профиль `optimized` используется по умолчанию
для локального RAG: temperature 0, контекст 8192, ответ до 1000 токенов,
thinking отключён, prompt `complete-v3`.

## Что изменено

| Параметр | Исходный профиль | Оптимизированный |
|---|---|---|
| Модель | Qwen 3.5 9B Q4_K_M | Та же Qwen 3.5 9B Q4_K_M |
| Temperature | 0 | 0 после проверки 0.1 и 0.2 |
| Окно контекста | 32768 | 8192; рост до 32768 для обязательных данных |
| Максимальный ответ | 3000 токенов | 1000 токенов |
| Thinking | Выключен | Выключен |
| Prompt | Форматирование ответов и выбор цитат | Объяснение конкурентного кода, ожидания и результата |

Интерпретация и генерация RAG используют один профиль, чтобы обычный ход
не переключал одну модель между разными размерами контекста. Для длинных
обязательных источников и памяти размер увеличивается до 16384/32768 по
консервативной оценке UTF-8. Старые отдельные сообщения истории обрезаются;
системные данные и текущий запрос сохраняются. Превышение верхнего бюджета
возвращает явную ошибку, а не незаметную потерю источников.

Настройки сохраняются в SQLite до начала генерации и переживают повтор
после ошибки или перезапуска. Незавершённые старые ходы без снимка профиля
используют прежний prompt и лимит 3000. Основной чат и облачный RAG имеют
собственную конфигурацию. Q4 уже применялась в дне 28: в этом эксперименте
проверяется компромисс двух уровней квантования одной 9B-модели, Q4 и Q8.

Новый prompt требует отвечать только по переданным выдержкам, сохранять
Java-идентификаторы, объяснять блокирующие вызовы и их место в процессе,
покрывать запрошенные условия и результаты и убирать повторяющийся фон.
Каждый тезис связан с ID готовой цитаты; сервер проверяет её происхождение
и прикрепляет текст из локального индекса. Память и документы остаются
данными, а не инструкциями. Отсутствие ответа в источниках требует отказа.

## Подбор параметров

[Первый прогон](day29-artifacts/calibration.json) содержит семь вопросов
из дня 28 и семь вариантов: baseline, compact, ctx16k, cap1500, temp01,
temp02 и первый новый prompt. Повышенная temperature не устранила пропуск
ожидания Future.get; контекст 16384 и ответ до 1500 не дали дополнительных
фактов. Первый новый prompt добавлял фон и тоже пропускал ожидание.

Во [второй версии](day29-artifacts/calibration-prompt-v2.json) появилось
объяснение future.get(), но на вопрос о подсчёте результатов возникло
лишнее обобщение о блокирующих take/poll. Оно повторяет неточную общую
формулировку одного фрагмента; методы и перегрузки нужно различать.
Например, poll() отличается от poll(timeout, unit), согласно
[Java API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/BlockingQueue.html).

[Третья версия](day29-artifacts/calibration-prompt-v3.json) ограничила ответ
запрошенными фактами, убрала это дополнение и сохранила ожидание future.get().
[Выбор профиля](day29-artifacts/selection.json) зафиксирован до запуска
контрольных вопросов. Параметры применены к одному кейсу: это не универсальные
оптимальные настройки для всех задач.

В первом калибровочном прогоне RSS/CPU собирались только для сервера Ollama;
соответствующие поля явно подписаны `server`. Данные выделения модели из
/api/ps корректны. Итоговый прогон дополнительно учитывает дочерний
llama-server; данные этих двух способов сбора RSS не объединяются.

## Сравнение после фиксации настроек

| Вариант | Медиана генерации | p95 | Токенов/с | Выделение модели | RSS процессов | Полнота | Верные отказы |
|---|---:|---:|---:|---:|---:|---:|---:|
| До · Q4 | 7.50 с | 12.47 с | 38.13 | 7.34 ГБ | 9.59 ГБ | 33/42 | 12/12 |
| Параметры · Q4 | 7.50 с | 12.40 с | 38.17 | 6.45 ГБ | 8.78 ГБ | 33/42 | 12/12 |
| После · Q4 | 7.23 с | 12.59 с | 38.15 | 6.45 ГБ | 8.85 ГБ | 33/42 | 12/12 |
| После · Q8 | 9.15 с | 17.47 с | 26.12 | 10.34 ГБ | 12.72 ГБ | 30/42 | 12/12 |

Время и ресурсы — из 72 контрольных наблюдений: шесть вопросов, три повтора,
одинаковое питание от сети и power mode 0. Качество — из 216 ответов на
18 вопросов. Параметры, исходные ответы и метрики сохранены в
[evaluation.json](day29-artifacts/evaluation.json) и
[timing-control.json](day29-artifacts/timing-control.json).

**Вывод по этому прогону:** контекст 8192 уменьшил выделение модели на
**12.1%**, с 7.34 до 6.45 ГБ; пик RSS в контрольном наборе снизился с
**9.59 до 8.85 ГБ**. Медиана генерации с новым prompt стала 7.23 вместо
7.50 с — небольшой сдвиг на этой выборке; скорость декодирования практически
совпала, около 38 токенов/с. Само уменьшение лимита ответа и контекста
не ускорило декодирование.

Общая полнота сохранилась: **33/42**. На калибровочных вопросах обе Q4 дали
**18/21** полных ответов, на контрольных — **15/21**. Новый prompt добавил
ожидание future.get() в вопросе 3, но в вопросе 5 перестал явно называть
отдельную задачу для каждого изображения. Ответы о Timer остаются неполными.
Все варианты лишний раз отказались на вопросе 17 об отмене работающей задачи,
хотя источники позволяют ответить. Эти отказы включены в потери полноты.

По [оценке цитат](day29-artifacts/quality-review.json) все сформулированные
основные факты корректны: 39/42 у каждого варианта; три остальных — лишние
отказы. У исходной Q4 широкая формулировка о времени отрисовки страницы
недостаточно поддерживается выбранной цитатой о времени загрузки изображений.
Ответов, одновременно полных, корректных и поддержанных цитатами: исходная
Q4 **30/42**, оптимизированная Q4 **33/42**. Это оценка Codex, не независимого
эксперта.

Q8 потребовала 10.34 ГБ выделения модели и показала медиану 9.15 с,
около 26 токенов/с и полноту 30/42. На этом наборе дополнительная точность
весов не дала преимущества. Для рабочего профиля оставлена Q4.

В полном прогоне ошибок провайдера, обрезанного JSON и отказов проверки
формата/происхождения цитат нет: 216/216 ответов валидны с первой попытки.
Статус совпал с ожидаемым в 204/216; остальные 12 — лишние отказы на вопросе 17.
Тексты и выбранные цитаты совпали во всех трёх повторах каждого варианта.
Пики RSS полного набора отличаются от контрольных: они сохранены в исходном
JSON и не подменяют сравнение на одинаковом контрольном наборе.

## Настоящий HTTP-путь и запуск

[Сквозная проверка](day29-artifacts/application-check.json) прошла 18 HTTP-ходов:
по три повтора FutureRenderer, Timer и StructuredTaskScope на baseline и optimized.
Содержательные ответы получили проверенные цитаты; StructuredTaskScope — отказ.
Выбранные локальная модель и профиль сохранены в каждом ходе. Для каждого
повтора создавался отдельный чат. Демо-базы находятся в игнорируемых
`data/day29-baseline.sqlite3` и `data/day29-optimized.sqlite3`.

baseline: медиана полного HTTP-хода на содержательных вопросах **11.50 с**; холодная/прогретая генерация на FutureRenderer — **6.97/2.76 с**.

optimized: медиана полного HTTP-хода на содержательных вопросах **11.50 с**; холодная/прогретая генерация на FutureRenderer — **10.19/6.01 с**.

Сквозная задержка практически одинакова; прирост скорости всего RAG здесь
не показан. Холодная/прогретая пара — по одному наблюдению на профиль.
Второй вызов использует кэш prompt; в более полном ответе на FutureRenderer
больше выходных токенов. Старт retrieval с загрузкой локальных весов занял
**6.49 с** и исключён из прогретых HTTP-ходов.

## Методика и ограничения

[Набор](../evaluation/day29-cases.json) содержит 18 вопросов: семь для
настройки и одиннадцать для проверки. В проверке восемь новых вопросов и
три прежних отрицательных случая, которые теперь передаются генератору
с непустым нерелевантным контекстом. Таким образом, отказ здесь действительно
проверяет LLM, а не ранний выход поиска без вызова генератора.

Четыре конфигурации получают одинаковые зафиксированные фрагменты книги,
без истории и памяти. Calibration-фрагменты взяты из сохранённого retrieval
дня 28; проверочные фрагменты выбраны явно и включены в набор. Это изоляция
генерации, а не оценка recall поиска. Для каждого сочетания выполняются
три повтора; порядок блоков профилей и вопросов меняется. Seed одинаков
для парных вариантов одного повтора. Перед блоком выгружаются загруженные
модели и выполняется отдельный короткий прогрев, не входящий в основное
время. Часть общей инструкции может использовать прогретый prefix cache.

В полном прогоне менялась скорость декодирования, а позднее был обнаружен
режим энергосбережения на аккумуляторе. Начальное состояние питания не
записано; задержки этого прогона остаются разведочными и не используются
как основное сравнение скорости. Наблюдение сохранено в
[timing-observation.json](day29-artifacts/timing-observation.json).

Для скорости выполнен отдельный [контрольный прогон](day29-artifacts/timing-control.json):
вопросы 2, 3, 6, 11, 13 и 16 охватывают короткое объяснение, конкурентный
код, подсчёт результатов, завершение Executor, длинный ответ о Timer и
сравнение двух реализаций. Каждый вариант получает те же шесть вопросов
по три повтора. Перед и после каждого вызова проверяются источник питания
и режим macOS. Первые 39 наблюдений контрольного запуска на аккумуляторе
сохранены [отдельно](day29-artifacts/timing-control-battery-partial.json):
смена питания остановила запуск, затронутый ответ не был сохранён, а
неполный набор исключён из основного сравнения. Итоговый запуск начинается
заново при питании от сети. Остальная активность компьютера не изолируется.

[Рубрика](../evaluation/day29-rubric.json) задаёт необходимые факты по
вопросам. Полнота, правильность и смысловая поддержка цитат оцениваются
отдельно по каждому уникальному ответу. Совпавшие ответ и цитаты одного
вопроса используют одну оценку во всех повторах. Автоматическая проверка
статуса/JSON и точного совпадения цитат не заменяет оценку смысла.

Смысловую оценку выполняет Codex. Независимой проверки человеком нет.
Выборка небольшая и относится к одной главе; часть вопросов повторно
использовалась при настройке. Контрольные вопросы оцениваются отдельно,
но не представляют случайную выборку. Медианы и p95 описывают этот прогон
и не являются статистической гарантией будущей скорости или качества.

Время генерации включает вызов модели и проверку ответа, но исключает
интерпретацию и retrieval. Отдельная сквозная проверка использует настоящий
HTTP API, Qwen, E5, FAISS, reranker и SQLite. В ней отсутствует облачный
ключ; внешние socket-соединения отдельно не блокируются. Холодный замер
выгружает веса, но сохраняет файловый кэш операционной системы.

Память модели — выделение из /api/ps; RSS — сумма сервера и его дочерних
процессов с шагом 0.25 секунды. На Apple Silicon Metal использует общую
память: RSS и выделение модели пересекаются, их нельзя суммировать.
Сэмплирование может пропустить короткий пик. CPU time также сэмплируется;
это время процессов, а не загрузка GPU или энергопотребление. Потребление
энергии и аппаратные счётчики GPU в этом эксперименте не измеряются.

Окружение: Apple M4 Pro, 48 GiB RAM, Ollama 0.35.1. Версии библиотек,
размеры и digest весов находятся в [environment.json](day29-artifacts/environment.json).
Модели загружаются до прогона; все измеренные вызовы LLM идут по loopback.

## Видео, отчёт и повторение

[Интерактивный отчёт](day29-artifacts/report.html) показывает исходные и
оптимизированные ответы, цитаты, времена и результаты проверки.
[Видео](day29-artifacts/day29-demo.mp4) представляет измеренные результаты
и сохранённые ответы; это монтаж с русским текстом, без звука, а не
непрерывная запись экрана. PNG/SVG кадров и SRT сохраняются рядом с видео.

```bash
# После запуска локального Ollama:
ollama pull qwen3.5:9b-q4_K_M
ollama pull qwen3.5:9b-q8_0
python scripts/run_day29_evaluation.py --output /tmp/day29-evaluation.json
python scripts/run_day29_evaluation.py --question-ids 2 3 6 11 13 16 \
  --power-guard --output /tmp/day29-timing-control.json
python scripts/check_day29_application.py
# Для сохранённого прогона с уже подготовленными ручными оценками:
python scripts/build_day29_quality_review.py
python scripts/build_day29_report.py
python scripts/build_day29_video.py
```

Для нового JSON нужна новая смысловая оценка: аннотации привязаны к текстам
и цитатам, а итоговая оценка — к SHA-256 отчёта и рубрики. Сборщики не
применяют старую оценку к изменившемуся прогону. Для видео нужны ffmpeg
и rsvg-convert. Прогон временно выгружает загруженные модели Ollama;
выполняйте его без других запросов к тому же серверу.

Для возврата к исходным настройкам задайте `RAG_LLM_PROFILE=baseline`
перед запуском приложения. `compact` меняет параметры, сохраняя исходный
prompt. Повтор хода использует сохранённый профиль, даже после смены
настроек сервера.
